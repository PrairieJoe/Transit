# PRD — 교통카드·BIS·KTDB GTFS 기반 대중교통 종합분석 및 버스 개편 시나리오 분석 시스템

- 문서 버전: v1.0
- 작성일: 2026-08-26
- 상태: 구현 기준안
- 제품 유형: 웹 기반 교통분석·시나리오 의사결정 지원 시스템
- 주요 엔진: OpenTripPlanner(OTP), OSRM, PostgreSQL/PostGIS
- 주요 입력: 교통카드 데이터, 지역별 BIS 데이터, KTDB 철도/도시철도 GTFS, OpenStreetMap(OSM)
- 분석 대상: 버스 + 도시철도/철도
- 개편 시나리오 대상: 버스 우선
- 주요 사용자: 교통계획/연구 실무자, 지자체·지역 버스 담당자

---

## 1. 문서 목적

본 문서는 교통카드 데이터를 실제 대중교통 수요의 관측자료로 활용하고, 지역별 BIS 데이터 및 교통카드의 노선·정류장 정보를 표준화하여 버스 운행망을 재구성하며, KTDB GTFS의 철도·도시철도 네트워크와 결합하여 대중교통 현황과 버스 개편 시나리오를 분석하는 웹 시스템의 제품 요구사항을 정의한다.

본 시스템은 단순한 노선 조회 또는 대중교통 길찾기 서비스가 아니다. 핵심 목적은 다음과 같다.

1. 교통카드로 관측된 현황 수요를 정확히 집계한다.
2. 관측된 수요와 네트워크를 이용하여 OTP 기반 경로선택 모형을 검증·보정한다.
3. 버스 노선, 정류장, 배차간격, 운행시간대, 운행횟수, 차량대수 등을 변경한 시나리오를 구성한다.
4. 변경된 네트워크에 기존 수요를 다시 배정한다.
5. 버스와 철도/도시철도 간 경로전환을 포함한 대중교통 전체의 영향을 분석한다.
6. 이용자 편익, 노선별 수요, 혼잡도, 운영량, 필요차량 및 지역별 수혜·피해를 정량적으로 비교한다.

## 2. 핵심 제품 정의

### 2.1 한 문장 정의

> 교통카드의 실제 이용수요를 기준으로 현황 대중교통 이용을 재현·검증하고, 버스 개편안을 OTP/OSRM 기반으로 시뮬레이션하여 수요·서비스·운영지표의 전후 변화를 분석하는 GIS 중심 웹 분석도구.

### 2.2 핵심 원칙

1. **관측값은 관측값으로만 표시한다.**
   - 교통카드에 실제 기록된 값과 시스템이 추정·보정한 값을 화면과 데이터 모델 모두에서 분리한다.
   - 사용자가 명시적으로 `현황(관측)` 화면을 선택했을 때는 추정값을 섞지 않는다.

2. **시나리오 분석에는 분석 가능한 보정 수요를 자동 사용한다.**
   - 실제 하차기록이 존재하는 Journey와 신뢰도 기준을 통과한 하차추정 Journey를 이용한다.
   - 낮은 신뢰도 또는 추정 불가능 자료는 임의로 목적지를 생성하지 않고 Unknown으로 남긴다.

3. **버스 원천정보는 유효한 BIS가 있으면 BIS를 우선한다.**
   - 정류장, 노선, 경유순서, 형상 등 버스 공간 네트워크 정보는 BIS를 우선한다.
   - BIS가 비어 있거나 필드가 유효하지 않을 때 교통카드의 노선·정류장 정보를 사용한다.
   - 명시적인 관리자 수동보정은 모든 자동 우선순위보다 우선한다.

4. **GTFS는 버스 원천자료가 아니라 분석용 표준 인터페이스다.**
   - 버스는 BIS/교통카드 원천을 내부 표준 모델로 변환한 뒤 분석용 GTFS를 생성한다.
   - GTFS 자체가 OSRM 입력이 되는 것은 아니다.
   - OSRM은 OSM 도로망과 정류장/경유점 좌표를 이용해 버스 경로 형상, 도로거리, 기준 주행시간을 추정한다.
   - 완성된 버스 GTFS와 KTDB 철도 GTFS는 OTP 입력으로 사용한다.

5. **철도/도시철도는 시나리오에서 고정망으로 취급한다.**
   - 기본값은 KTDB GTFS를 사용한다.
   - 버스 시나리오에 따라 승객이 버스↔철도/도시철도 간 경로를 변경하는 것은 허용한다.
   - 철도 자체의 개편 시나리오는 MVP 범위에서 제외한다.

6. **초보 사용자는 복잡한 교통모형 파라미터를 몰라도 분석할 수 있어야 한다.**
   - 일반 모드는 자동추정·권장값 중심으로 구성한다.
   - Logit 계수, 평균속도, 환승패널티, 정차시간, 회차시간 등의 상세 설정은 `고급 설정`에서 제공한다.

## 3. 문제 정의

현재 지역별 대중교통 분석은 다음과 같은 문제를 가진다.

- 교통카드는 실제 수요를 포함하지만 지역마다 데이터 스키마가 다르다.
- 일부 지역은 하차태그 의무가 없어 하차기록 누락이 매우 크다.
- BIS의 제공 필드·품질·형식이 지역마다 상이하다.
- 일부 지역은 노선 형상(shape)이 없고 정류장 목록과 순서만 존재한다.
- 철도와 버스를 함께 분석하려면 서로 다른 데이터 체계를 하나의 네트워크로 결합해야 한다.
- 실제 교통카드 수요와 경로탐색모형의 결과를 비교하지 않은 상태에서 버스 개편효과를 산정하면 모형 결과의 신뢰성을 확인하기 어렵다.
- 지자체 버스 담당자에게 전문 교통모형 도구는 진입장벽이 높다.
- 버스 개편안은 수요 변화뿐 아니라 배차간격, 회차시간, 필요차량, 총 보유차량과 같은 운영가능성도 함께 검토해야 한다.

본 제품은 위 문제를 하나의 분석 파이프라인으로 통합한다.

## 4. 사용자

### 4.1 Primary Persona — 교통계획/교통연구 실무자

특징:
- 교통수요 분석, 노선개편, 데이터 검증 업무 수행
- GIS와 교통자료에 익숙할 수 있음
- 분석가정을 직접 변경하고 결과를 세밀하게 검토하려는 요구가 있음

필요:
- 원천 데이터 품질 확인
- OD/Journey 및 노선별 수요 검증
- 모형 적합도 지표
- 다양한 시나리오 저장·복제·비교
- 고급 파라미터 조정
- 공간데이터 및 상세 결과 내보내기

### 4.2 Secondary Persona — 지자체/지역 버스 담당자

특징:
- 대중교통 및 프로그래밍 전문지식이 낮을 수 있음
- “이 노선을 이렇게 바꾸면 어떻게 되는가?”를 빠르게 확인하는 것이 핵심
- 복잡한 설정값보다 시스템 추천값과 시각적 결과를 선호

필요:
- 단계형 분석 마법사
- 쉬운 오류 설명
- 지도에서 정류장을 선택해 노선을 구성
- 차량대수/배차간격 자동 계산
- 현재 대비 개선/악화가 명확한 결과
- 보고용 표와 지도 내보내기

### 4.3 역할

MVP 역할:
- `Admin`: 데이터셋 등록, 매핑 확정, 수동보정, 시스템 기본값 관리
- `Analyst`: 분석영역 생성, 시나리오 생성·실행, 결과 조회·내보내기
- `Viewer`(선택): 결과 열람만 가능

## 7. 데이터 입력 및 데이터셋 보관소

### 7.1 기본 방식

MVP는 `등록된 데이터셋 재사용 + 신규 파일 업로드` 방식으로 한다.

예시:

```text
데이터셋 보관소
├─ A시 / 2026-03
│   ├─ 교통카드 원천
│   ├─ BIS 원천
│   ├─ 컬럼 매핑
│   ├─ 노선/정류장 Crosswalk
│   ├─ 하차추정 설정
│   ├─ 품질검사 결과
│   └─ 정제 Parquet
├─ B도 / 2026-04
│   └─ ...
└─ KTDB 철도 / 2024-03
```

### 7.2 신규 데이터 등록 흐름

1. 파일 업로드
2. 인코딩/구분자/컬럼 타입 자동감지
3. 표준 필드 후보 자동매핑
4. 사용자 확인
5. 값 유효성 검사
6. 좌표계/좌표 범위 검사
7. 노선/정류장 Crosswalk 생성
8. 중복/결측/비정상값 검사
9. 품질 리포트
10. 사용자가 등록 확정
11. 정제본을 Parquet 및 DB로 저장

### 7.3 향후 연계

외부의 별도 교통카드 수집/가공 시스템이 존재할 경우 동일한 `Dataset Import API`를 통해 본 시스템의 데이터셋 보관소에 결과물을 등록할 수 있도록 인터페이스를 분리한다.

자동 외부 API 수집 자체는 본 MVP에서 중복 구현하지 않는다.

### 8.2 모든 파생 데이터가 가져야 하는 공통 메타데이터

  - `BIS`
  - `CARD`
  - `KTDB_GTFS`
  - `MANUAL`
  - `OSRM_INFERRED`
  - `MODEL_INFERRED`
- `source_dataset_id`
- `derivation_method`
- `quality_status`
- `confidence_score`
- `is_manual_override`
- `created_at`

### 8.3 품질상태

- `exact`
- `confident`
- `ambiguous`
- `unmatched`
- `invalid`

`ambiguous`, `unmatched`, `invalid`는 자동으로 분석 네트워크에 편입하지 않는다. 관리자가 명시적으로 확정하면 사용 가능하다.

## 9. 버스 정보 원천 우선순위

### 9.1 자동 우선순위

유효성 검사를 통과한 데이터에 한하여 다음 우선순위를 사용한다.

| 항목 | 1순위 | 2순위 | 3순위 |
|---|---|---|---|
| 노선 기본정보 | BIS | 교통카드 | 수동 |
| 정류장 기본정보 | BIS | 교통카드 | 수동 |
| 노선별 정류장 순서 | BIS | 교통카드 | 수동 |
| 노선 형상 | BIS | OSRM 추정 | 수동 |
| 정류장간 실제 시간 | BIS/운행자료 | 평균속도 기반 | OSRM 보정 |
| 운행시간대/배차 | BIS/운행계획 | 사용자 입력 | 시스템 기본 |

단, 명시적 `수동 Override`가 존재할 경우 수동값이 모든 자동값보다 우선한다.

### 9.2 BIS가 부분적으로 비어 있는 경우

BIS 전체를 폐기하지 않고 필드 단위로 fallback한다.

예:
- route/stop/sequence는 BIS 사용
- shape만 비어 있음 → OSRM으로 shape 생성
- stop 좌표 일부 오류 → 해당 stop만 교통카드 또는 수동보정

### 9.3 Crosswalk

원천 ID를 직접 동일 ID로 간주하지 않는다.

예:
- `source_route_id` → `canonical_route_id`
- `source_stop_id` → `canonical_stop_id`

Crosswalk에는 매칭 근거 및 신뢰도를 저장한다.

## 10. KTDB 철도/도시철도 GTFS

### 10.1 역할

KTDB GTFS는 전체 대중교통 원천자료가 아니라 **철도 및 도시철도의 기준 네트워크**로 사용한다.

버스는 KTDB GTFS의 버스자료를 기본 네트워크로 사용하지 않는다.

### 10.2 처리

1. KTDB GTFS ZIP 등록
2. 철도/도시철도 mode만 추출
3. ID를 내부 namespace로 재작성
4. 스키마 유효성 검사
5. 정류장/역 좌표 검사
6. 버스 네트워크와 환승 가능한 stop/station 후보 생성
7. OTP용 통합 feed 생성

### 10.3 수동 보완

철도망은 빈번하게 변경되지 않는다는 전제하에 다음을 지원한다.

MVP:
- 새로운 철도 GTFS 파일로 교체
- 관리자용 GTFS patch/추가 feed 업로드
- 역/노선/운행정보의 제한적 수동 보정

MVP 이후:
- 지도 기반 철도노선 GUI 편집

### 10.4 버전 고정

모든 분석에는 사용한 KTDB GTFS 버전을 기록한다.

시나리오 비교에서 Base와 Scenario는 동일 철도 GTFS 버전을 사용해야 한다.

## 11. OSRM 역할

OSRM은 GTFS를 입력받지 않는다.

본 시스템에서 OSRM의 역할은 다음과 같다.

1. 정류장 좌표를 OSM 도로망에 snapping
2. 노선 형상 미존재 시 정류장 순서를 따라 버스 경로 형상 추정
3. 도로상 거리 산정
4. 기준 도로 주행시간 산정
5. 필요 시 후보 정류장 간 네트워크 거리 계산

### 11.1 버스 shape 생성

전체 정류장을 하나의 거대한 요청으로 연결하기보다 기본적으로 **인접 정류장 쌍 단위 Route**를 수행한 후 geometry를 연결한다.

장점:
- 정류장 순서를 확실하게 유지
- 경로 오류 구간을 부분적으로 재처리 가능
- 긴 노선 API 제한 회피
- U-turn/루프 오류 탐지가 쉬움

### 11.2 오류 처리

다음 경우 자동 승인하지 않는다.

- stop이 도로망에서 과도하게 먼 경우
- 두 인접 stop 간 OSRM 경로가 비정상적으로 긴 경우
- 노선 진행이 명백히 역행하는 경우
- 경로 생성 실패
- 도로망 단절

상태:
- `osrm_estimated`
- `needs_review`
- `failed`

### 11.3 OSRM 시간의 의미

OSRM의 기본 주행시간을 실제 버스 운행시간의 참값으로 취급하지 않는다.

버스 통행시간 추정 우선순위:

1. 신뢰 가능한 BIS/운행계획 정류장간 소요시간
2. 사용자가 설정한 시간대별 버스 평균통행속도 + 정차시간
3. OSRM 주행시간 × 버스 보정계수 + 정차시간
4. 시스템 기본 버스 평균속도 + 정차시간

## 12. 분석용 버스 GTFS 생성

### 12.1 목적

내부 표준 버스 네트워크를 OTP가 읽을 수 있는 GTFS Schedule 구조로 변환한다.

### 12.2 최소 생성 파일

- `agency.txt`
- `stops.txt`
- `routes.txt`
- `trips.txt`
- `stop_times.txt`
- `calendar.txt` 또는 `calendar_dates.txt`
- `shapes.txt`

배차기반 시나리오에서는 필요 시:
- `frequencies.txt`

### 12.3 timepoint

정확한 정류장 시각이 아닌 평균속도/보간으로 생성한 시간은 GTFS의 approximate time이라는 사실을 나타낼 수 있도록 별도 메타데이터와 `timepoint` 정책을 적용한다.

### 12.4 시나리오 배차

정확한 개별 출발시각표가 없는 배차간격 기반 시나리오는 GTFS frequency-based representation을 우선 검토한다.

### 12.5 방향/패턴

한 노선에 상·하행 또는 복수 경로가 존재할 수 있으므로 `Route`와 `RoutePattern`을 분리한다.

예:
- Route: 100번
- Pattern A: 기점→종점
- Pattern B: 종점→기점
- Pattern C: 특정 시간대 단축운행

## 13. OTP 역할

OTP(OpenTripPlanner)는 다음 역할을 담당한다.

- 보행 + 버스 + 철도/도시철도 통합 경로탐색
- OD별 후보 대중교통 경로 생성
- 시나리오 네트워크에서 대체경로 생성
- 버스 개편 후 버스↔철도 전환을 포함한 경로 후보 계산

OTP 결과를 그대로 최종 수요배정 결과로 간주하지 않는다.

OTP는 **choice set generator** 역할을 하며, 최종 수요 분배는 별도의 generalized cost + Logit 모형에서 수행한다.

### 13.1 OTP API 연동 원칙

신규 애플리케이션 연동은 OTP의 GTFS GraphQL API를 기준으로 설계한다.

- 신규 코드는 과거 OTP REST API에 의존하지 않는다.
- API 호출부는 Backend Adapter로 격리하여 OTP 버전 변경의 영향을 최소화한다.
- OTP 자체 응답은 분석 DB의 영구 결과로 직접 간주하지 않고, 후보경로 원본과 변환된 choice-set을 버전과 함께 저장한다.

## 14. 분석영역

### 14.1 생성방법

모두 지원한다.

1. 시·도/시·군·구 등 행정구역 선택
2. 지도에서 Polygon 직접 그리기
3. GeoJSON/Shapefile 업로드

### 14.2 네트워크 Buffer

사용자가 지정한 Polygon 경계에서 네트워크를 즉시 절단하지 않는다.

```text
실제 결과 집계영역 = 사용자 Polygon
라우팅 네트워크 = 사용자 Polygon + Network Buffer
```

Buffer 거리는 시스템 기본값을 제공하되 고급 설정에서 변경 가능하게 한다.

### 14.3 OD 포함기준

Base 규칙:

> 출발지 또는 도착지 중 하나 이상이 분석영역 내부이면 포함.

따라서:
- 내부→내부: 포함
- 내부→외부: 포함
- 외부→내부: 포함
- 외부→외부 단순 통과: 기본 제외

단, 경로 계산 과정에서 외부 네트워크를 이용하는 것은 허용한다.

## 16. Journey 구성

### 16.1 단위

두 계층을 모두 유지한다.

1. `Ride/Leg`: 개별 승차 건
2. `Journey`: 환승을 포함한 연속 통행

### 16.2 환승 판단 우선순위

1. 교통카드의 명시적 환승/통행체인 필드
2. 거래순번 및 시각 연속성
3. 시스템의 지역별 환승 규칙

자동 추론을 사용한 경우 derivation method를 기록한다.

### 16.3 하차기록이 없는 지역

하차태그가 없는 사실 자체를 오류로 처리하지 않는다.

각 Leg의 목적지 상태는:

- `OBSERVED`
- `INFERRED_HIGH_CONFIDENCE`
- `UNKNOWN`

으로 구분한다.

## 17. 하차누락 추정

MVP에서는 **다음 승차(next boarding) 기반 추정만** 수행한다.

반복일 패턴이나 다음날 첫 승차를 이용한 고급 추정은 하지 않는다.

### 17.1 기본 논리

현재 Leg를 `L1`, 그 다음 승차를 `L2`라고 한다.

`L1`의 노선 정류장 순서가 존재하고 `L1` 하차기록이 없는 경우:

#### Step 1 — 동일 정류장 직접 일치

1. L1 승차정류장 이후의 정류장 목록을 생성한다.
2. L2의 승차정류장이 해당 목록에 존재하는지 확인한다.
3. 존재하면 그 정류장을 L1의 추정 하차정류장으로 사용한다.

단:
- L1 승차정류장보다 이전 순서의 stop은 후보에서 제외
- 순환노선은 pattern 및 stop sequence를 이용해 방향성을 판단
- 정류장 ID가 다르더라도 CanonicalStop Crosswalk로 동일 정류장인지 먼저 확인

#### Step 2 — 거리 기반 추정

직접 일치하지 않으면:

1. L1 승차 이후 downstream stop만 후보로 생성
2. L2 승차정류장과 후보 stop 사이의 직선거리를 계산하여 사전 필터
3. 상위 후보에 대해 보행 네트워크 거리 또는 접근거리 계산
4. 가장 가까운 합리적 후보를 선택
5. 시간적 실현가능성 및 최대 접근거리 기준 검사
6. 기준을 통과하면 `INFERRED_HIGH_CONFIDENCE`
7. 통과하지 못하면 `UNKNOWN`

### 17.2 금지사항

다음은 하지 않는다.

- 가장 가까운 정류장을 무조건 목적지로 생성
- 진행방향 반대 정류장 사용
- 시간상 도달 불가능한 정류장 사용
- 당일 마지막 Journey의 목적지를 임의 생성
- 낮은 confidence 자료를 시나리오 OD에 자동 포함

### 17.3 Confidence

신뢰도 계산 요소:
- 다음 승차정류장 exact match 여부
- Crosswalk match 품질
- 추정 stop과 다음 승차 stop의 접근거리
- 시간 간격
- 노선 진행방향
- 후보 간 거리 격차
- 경로 구조의 특이성(순환/중복 정류장 등)

MVP에서 분석 포함 기준값은 환경설정 가능하게 한다.

## 18. 관측값과 분석용 보정값 분리

### 18.1 현황(관측) 화면

사용자가 명시적으로 `현황(관측)`을 선택한 경우 교통카드에 실제 기록된 값만 표시한다.

예:
- 실제 승차건수
- 실제 기록 하차건수
- 실제 기록 환승건수
- 실제 이용노선별 승차건수

하차가 누락된 자료를 임의로 채우지 않는다.

하차정보가 필요한 KPI는 다음 중 하나로 처리한다.

- 데이터 커버리지와 함께 부분집계
- 산출불가(N/A)
- `관측 하한값`임을 명시

### 18.2 모델 재현 화면

분석용 OD:
- 실제 하차 Journey
- High-confidence 하차추정 Journey

Unknown은 제외한다.

OTP+Logit 배정결과를 관측값과 비교한다.

### 18.3 시나리오 화면

사용자가 시나리오 분석으로 진입하면 별도 조작 없이 **분석용 보정수요와 보정된 모델계수**를 자동 사용한다.

즉 시나리오 화면에서는:

```text
Observed raw demand
        +
High-confidence inferred alighting
        +
Calibrated route-choice model
        ↓
Analysis-ready demand
```

를 사용한다.

UI에는 `사용된 수요 커버리지`를 항상 표시한다.

## 20. 후보경로 및 Logit 수요배정

### 20.1 OTP 후보경로

각 OD/시간대별로 복수의 합리적 대중교통 경로를 생성한다.

후보경로는 다음을 포함할 수 있다.

- 버스 only
- 철도/도시철도 only
- 버스→철도
- 철도→버스
- 버스→철도→버스
- 복수 버스 환승

### 20.2 Generalized Cost

MVP 기본 구성:

- 차내시간
- 대기시간
- 도보시간
- 환승횟수/환승패널티

요금은 MVP 기본 경로선택 비용에서 제외한다.

### 20.3 계수

기본 정책:

1. 충분한 관측표본이 존재하면 지역별 자동 보정
2. 표본이 부족하면 시스템 기본계수 사용
3. 전문가용 고급설정에서 직접 수정 가능

### 20.4 자동 보정

관측된 선택과 OTP가 생성한 대안 경로를 이용하여 Multinomial Logit 계수를 추정하는 방식을 기본으로 한다.

과적합 방지를 위해:
- 최소 표본수
- 계수 부호 제약 또는 합리적 범위
- 정규화/regularization
- validation split

을 적용할 수 있다.

### 20.5 재현성

모델 실행 시 다음을 저장한다.

- 계수
- 데이터셋 버전
- OTP 그래프 버전
- 후보경로 생성설정
- 분석 시간대
- 제외된 수요 비율
- calibration metric
- random seed(사용 시)

## 24. 차량대수·배차간격 운영가능성 계산

본 기능은 MVP 핵심 기능이다.

### 24.1 Cycle Time

```text
Cycle Time
= 상행 주행시간
+ 종점 회차/휴게시간
+ 하행 주행시간
+ 기점 회차/휴게시간
```

순환노선은 1회 완전 순환시간을 사용한다.

### 24.2 배차간격 입력 → 최소 운행차량

```text
N_service = ceil(Cycle Time / Headway)
```

예:
- Cycle Time = 110분
- 배차 = 10분
- 최소 운행차량 = 11대

### 24.3 차량대수 입력 → 가능한 최단 배차

```text
Minimum Sustainable Headway
≈ Cycle Time / N_service
```

실제 운행표 생성 시 시간단위 반올림 및 출발시각 정렬규칙을 적용한다.

### 24.4 예비차

예비차율을 “운행차량 대비 추가 확보비율”로 정의한다.

```text
N_total_required
= ceil(N_service × (1 + reserve_rate))
```

화면에서는:
- 운행 필요차량
- 권장 예비차
- 총 필요차량

을 분리해 표시한다.

### 24.5 두 입력모드

#### Mode A — 배차간격 고정
사용자 입력:
- 배차간격
- 운행시간대

시스템 계산:
- Cycle time
- 최소 운행차량
- 총 필요차량

#### Mode B — 차량대수 고정
사용자 입력:
- 투입 가능 운행차량

시스템 계산:
- 최소 지속가능 배차간격
- 가능한 시간당 운행횟수

### 24.6 전체 차량 제약

지역 전체 보유차량 값을 설정할 수 있다.

예:

```text
총 보유차량 120대

기존 10번   -2
기존 20번   +3
신규 30번   +6
폐지 40번   -8
----------------
시나리오 총 필요 119대
→ 실행 가능
```

총 필요차량이 가용차량을 넘으면:
- `Fleet Constraint Violation`
- 부족 차량대수
- 제약을 위반한 시간대/노선

을 표시한다.

### 24.7 MVP 한계

이 계산은 노선 단위 운영가능성 검사이며 다음은 수행하지 않는다.

- 차량별 block scheduling
- 노선간 차량 interlining
- 운전자 교대
- 차고지 출고/입고
- 정비계획

## 25. 혼잡도

MVP에서는 혼잡도를 결과지표로만 사용한다.


필요 시:

- 법정/실무 정원 기준

을 별도 지원할 수 있다.

차종별 시스템 기본값을 제공한다.

- 노선별 차종 선택
- 정원 수정
- 시간대별 투입차종 수정

이 가능하다.

### 25.3 결과

- 평균 혼잡도
- 최대 혼잡구간
- 100% 이상 구간 비율
- 설정 임계치 이상 과밀구간
- 혼잡도 지도

- Polars/DuckDB 기반 대용량 카드 전처리
- GeoPandas는 제한적 GIS 가공에 사용

### 32.3 Database
- PostgreSQL
- PostGIS

### 32.4 File/Columnar Storage
- Parquet
- 로컬 또는 S3-compatible Object Storage

### 32.5 Job Worker
- Redis + Celery/RQ/Dramatiq 중 하나
- 네트워크 build, routing, assignment, export를 job으로 처리

### 32.6 Routing Engine
- OTP 2.x 계열
- OSRM 5.x 계열

### 32.7 Deployment

최소 배포단위:

```text
frontend
api
worker
postgres-postgis
redis
otp
osrm
object-storage(optional)
```

Docker Compose 기반 단일 서버/분석 서버 배포를 기본으로 설계하고, 향후 다중 서버로 확장 가능하게 한다.

OTP/OSRM과 대용량 파일처리를 고려할 때 핵심 백엔드를 순수 serverless 환경에 의존하지 않는다.

## 33. OTP Graph 관리

### 33.1 Base Graph

분석영역 + Buffer와 Base 버스 GTFS + KTDB 철도 GTFS + OSM으로 생성한다.

### 33.2 Scenario Graph

시나리오가 대중교통 정적 네트워크를 변경하므로 Scenario GTFS로 별도 graph build가 필요할 수 있다.

그래프 생성비용을 줄이기 위해:
- 분석영역 제한
- 입력 hash
- 캐시
- 동일 시나리오 재사용
- OSM snapshot 공유

를 사용한다.

### 33.3 사용자 경험

노선 편집 자체는 즉시 지도에서 preview한다.

실제 수요배정은 사용자가 `분석 실행`을 누르면 네트워크 검증 이후 계산한다.

## 34. Functional Requirements

### FR-001 데이터셋 등록
사용자는 새로운 교통카드/BIS/GTFS 데이터를 등록할 수 있어야 한다.

Acceptance:
- 파일 업로드 가능
- 스키마 검사 결과 제공
- 매핑 완료 전 분석불가
- 기존 데이터셋 재사용 가능

### FR-002 컬럼 매핑
지역별 교통카드 스키마를 내부 표준필드에 매핑할 수 있어야 한다.

### FR-003 정류장/노선 Crosswalk
자동매칭은 confidence를 제공해야 하며 ambiguous는 자동 확정하지 않아야 한다.

### FR-004 BIS 우선
유효 BIS가 존재하면 버스 네트워크 구성 시 BIS가 자동 우선되어야 한다.

### FR-005 OSRM shape 추정
shape가 없는 노선은 ordered stops를 이용해 OSRM 도로형상을 생성할 수 있어야 한다.

### FR-006 GTFS 생성
내부 버스 네트워크를 OTP용 GTFS로 생성할 수 있어야 한다.

### FR-007 철도 결합
KTDB 철도/도시철도 GTFS와 자체 버스 GTFS를 하나의 OTP 분석망에 결합할 수 있어야 한다.

### FR-008 Journey 생성
개별 승차건과 Journey를 모두 보존해야 한다.

### FR-009 하차추정
다음 승차기반 High-confidence 목적지 추정을 수행할 수 있어야 한다.

### FR-010 현황값 보호
Observed 화면에서 inferred 값이 실제값처럼 표시되어서는 안 된다.

### FR-011 모델 Calibration
OTP 대안경로와 실제 선택을 기반으로 지역별 Logit 계수를 자동 보정할 수 있어야 한다.

### FR-012 재현성 검증
관측값과 모델값의 적합도 지표를 제공해야 한다.

### FR-013 분석영역
행정구역, Polygon draw, GeoJSON/Shapefile을 지원해야 한다.

### FR-014 신규 버스노선
사용자가 정류장을 순서대로 선택하여 신규 노선을 작성할 수 있어야 한다.

### FR-015 경로 자동생성
신규/수정 노선은 OSRM으로 도로를 따라 shape를 생성해야 한다.

### FR-016 배차 편집
시간대별 배차간격을 수정할 수 있어야 한다.

### FR-017 차량대수 계산
배차간격 입력 시 최소 필요차량을 계산해야 한다.

### FR-018 최소 배차 계산
차량대수 입력 시 가능한 최단 지속가능 배차간격을 계산해야 한다.

### FR-019 총 Fleet Constraint
시나리오 전체 필요차량이 가용차량을 초과하는지 검사해야 한다.

### FR-020 시나리오 재배정
변경망에서 버스와 철도를 포함한 후보경로를 재생성하고 수요를 재배정해야 한다.

### FR-021 혼잡도
차량정원을 이용해 구간별 Load Factor를 계산해야 한다.

### FR-022 비교
Base와 Scenario의 주요 KPI delta를 보여줘야 한다.

### FR-023 내보내기
표/GIS/GTFS 결과를 파일로 내보낼 수 있어야 한다.

### FR-024 버전
모든 분석결과는 원천자료 및 설정 버전을 추적할 수 있어야 한다.

## 35. Non-Functional Requirements

### NFR-001 재현성
동일 데이터, 동일 설정, 동일 엔진버전에서 동일 분석을 재현할 수 있어야 한다.

### NFR-002 데이터 계보
모든 추정/보정값은 원천 및 derivation method를 추적할 수 있어야 한다.

### NFR-003 개인정보
- 원본 카드 식별자는 UI에 노출하지 않는다.
- 분석용 ID는 가명화/해시 처리한다.
- 사용자에게는 집계자료 중심으로 노출한다.
- 소수셀 결과 공개 제한 임계값을 배포기관 정책에 맞게 설정 가능하게 한다.

### NFR-004 실패 안전성
네트워크 일부 오류가 전체 원천 데이터를 손상시키지 않아야 한다.

### NFR-005 사용성
일반 사용자는 코드를 작성하지 않고 전체 분석을 수행할 수 있어야 한다.

### NFR-006 전문가 기능 분리
고급 모형 설정은 일반 화면에서 숨긴다.

### NFR-007 대용량 처리
교통카드 원천은 DB row-by-row 처리 대신 Parquet/columnar batch 처리를 우선한다.

### NFR-008 UI 응답성
대용량 지도는 집계·타일화하여 브라우저 메모리 과부하를 피한다.

### NFR-009 Job 복구
장시간 분석작업은 단계별 상태와 오류사유를 저장해야 한다.

### NFR-010 감사
수동 매칭/Override는 사용자, 시각, 이전값, 변경값을 기록한다.

## 36. 데이터 검증 규칙

### 정류장
- lat/lon 유효범위
- 동일 ID 좌표 급변
- 중복 좌표
- 이름만 같고 과도하게 먼 정류장
- 도로망과 과도하게 먼 정류장

### 노선
- stop sequence 최소 2개
- 중복/역행 sequence
- 비정상적 segment 거리
- loop 판정
- 동일 route의 서로 다른 pattern 구분

### shape
- stop과 shape 이격거리
- 자기교차/비정상 역행
- OSRM 경로실패
- 지나치게 긴 detour

### 교통카드
- 승차시각 > 하차시각 오류
- 존재하지 않는 stop/route
- 중복 거래
- 시간순서 역전
- 동일 카드의 비현실적 위치 이동
- 하차기록률

### GTFS
- 필수파일
- FK 무결성
- stop sequence
- service/calendar
- route/trip reference
- 시간형식
- shape reference

## 37. 오류 및 Fallback 정책

### 원칙

> 자동추정 실패를 조용히 숨기지 않는다.

각 데이터는:
- 사용됨
- fallback 사용
- 제외됨
- 수동검토 필요

상태를 명확하게 표시한다.

예:

```text
A노선
정류장        BIS
정류장순서    BIS
형상          OSRM 추정
운행시간      평균속도 추정

품질: Acceptable
주의: 실제 BIS shape가 없어 도로망 기반 추정형상을 사용함
```

## 38. 시나리오 비교의 해석 규칙

### Base
보정된 현재 네트워크 + 분석용 수요

### Scenario
Base와 동일 수요량 + 변경 네트워크

MVP에서는 총 OD 수요 자체를 변화시키지 않는다.

즉:
- 서비스가 좋아졌다고 신규통행 생성 안 함
- 서비스가 나빠졌다고 통행 포기수요 생성 안 함
- 기존 수요가 가능한 대중교통 경로 중 다른 경로를 선택하도록 재배정

경로 자체가 불가능해진 OD는 `Unserved/No feasible transit path`로 별도 집계한다.

## 39. 요금

MVP Logit에서는 요금을 제외한다.

이유:
- 지역별 환승요금제 차이
- 수도권 등 복잡한 거리비례/통합환승
- 버스-철도 연계요금
- 정확한 승하차/경로가 필요한 운임계산

단, 원천 요금 필드는 저장 가능하며 향후 Fare Engine을 추가할 수 있도록 데이터 모델은 확장 가능하게 한다.
